# Schedule Board availability contract

This flow has two separate responsibilities and they must not be merged:

1. **Still Available / availability** always calls `requestOwnerAvailability()` for the property's linked owner. `listed_by_agent_id` does not change the recipient. The availability service remains responsible for DNC, pauses, same-day deduplication, source-session selection and routing the answer back to the requesting agent.
2. **Ask / comment** may route to the listing agent. This is a different action and must not be reused for availability.

When an owner confirms availability, the private answer to every waiting requester includes Schedule Board deep links generated by `backend/services/agentPropertyLinks.js`:

- `action=detail` opens the property and the availability controls.
- `action=book` opens the booking flow.
- `action=media` opens the listing media view and its photo download action.

The same links are required for the fresh-confirmation shortcut, where the board already has a recent owner confirmation and correctly avoids asking the owner twice.

When an owner answer is ambiguous, no property state is guessed. The requesting agent receives only the public property reference and detail link, with three exact choices: `Still available`, `Rented`, or `Not sure`. These choices respectively refresh availability and expose the available actions, remove the listing as rented, or move it to manual review. Owner names, phone numbers, addresses, and raw reply text never appear in this agent prompt.

Production's full `services/availability.js` currently lives on the backend host. It imports `withAvailableActions` from `./agentPropertyLinks` and applies it in both `NOTIFY_TEXT.replied_available` and the fresh-confirmation shortcut. Keep both call sites when syncing or replacing that service.

## Flow freeze

Visual or layout work on the CRM must not change availability recipients, command routing, owner outreach, status transitions, or notification recipients. Those changes require a separately scoped flow change plus the focused contract tests.

Group commands typed by a connected account require the WAHA `message.any` event. The webhook must reject backend-sent echoes before treating such an event as a human command. Commands received from another group participant may arrive only with an opaque `@lid`; resolve that LID through WAHA and run the existing admin check against the verified phone. An unresolved or non-admin identity remains denied. The reproducible production patch is stored in `patches/2026-10-16-whatsapp-command-dispatch.patch`.
